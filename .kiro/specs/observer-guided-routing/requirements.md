# 会话观察与引导路由需求

状态：需求已批准。用户先回复“接受你的建议”，确认 Skills 仅建议、不自动加载全文；同一 run 换档要求显式能力交接；新旧模式互斥，随后回复“批准设计”。[技术设计](design.md) 与 [实施任务](tasks.md) 已分别批准，用户已授权开始实施；完成情况以任务勾选及验证证据为准，不修改个人配置。

## 目标

将 `pi-gear-router` 定位为 Pi 会话的**观察、方法建议与模型能力调度层**：优先利用快速、低成本的 Jev，在模型请求边界理解最新消息对当前任务的影响，提醒执行模型考虑当前用户实际可用的 Skills，并为需求收敛、复杂调查、设计和实施等工作匹配模型与 thinking。

本项目不另建一套开发方法、不替用户批准方案、不替 Skills 推进流程。自动切换模型不等于自动开始实施；方法、审批和交付标准仍由用户、项目指引及其选择的 Skills 决定，并遵守 Pi 及权限扩展的约束。

## 背景与证据

- [任务感知路由](../task-aware-routing/requirements.md) 已区分任务与用户回合，提供有限继承、能力保护、sticky dispatch 和分支恢复。
- [阶段编排路由](../phase-orchestrated-routing/requirements.md) 增加了开发 phase、handoff、planning/recovery 强制只读、settle reminder 和 complete gate。它是当前源码的既有规格，不因本草案存在就失效。
- [可行性验证](../../../docs/intent-routing-feasibility.md) 中，新问题设计下 Jev 对首轮 Git/文档核对正确返回只读调查；现有基线也识别 review/planning，却被总置信门槛和 review 排除规则挡住。小样本不证明生产准确率、Skills 推荐效果或费用节省。
- Pi 默认把可自动调用 Skill 的名称、描述和路径提供给执行模型，由模型选择并读取正文；“可见、推荐、已读取、已遵循”是不同事实。Pi 不提供已验证的通用 Skill 阶段机。

## 产品方向与审批状态

已在本次会话确认的方向：

1. 本项目是观察者与路由器，不接管用户开发流程。
2. 尽量利用 Jev，不默认增加第二个聊天模型判断层。
3. 根据不同用户实际可用的 Skills 提供方法建议，不硬编码个人 Skill 集合。
4. 对复杂需求、计划与设计匹配较高模型能力；明确实施可以自动降低一个模型档位或 thinking，但保留能力下限。
5. 对话意图不是每句话都独立启动流程；应识别最新消息对已有任务的作用。

R1–R10、A1–A20 及文末默认值构成本次已批准的需求基线。具体配置迁移、字段契约、SDK 接线和参数上界由设计提出并单独审批；不得将需求批准当成设计与实现同时获批。

## 领域语言

正式词汇见 [CONTEXT.md](../../../CONTEXT.md)。本需求区分：

| 概念 | 含义 | 不意味着什么 |
|---|---|---|
| 方法阶段 | 项目／Skill 定义的需求、设计、测试等工作阶段 | 统一开发流程或固定工具权限 |
| 消息作用 | 最新消息是续接、解释、补范围、暂停、取消或新目标 | 每条消息都建立新任务 |
| 路由能力状态 | 本次及后续工作需要的能力 profile | 用户已授权实施或业务已完成 |
| 观察结果 | 有界、可追溯的结构化解释和候选建议 | 审批或安全证明 |
| 会话引导 | 执行模型可见的简短方法／澄清建议 | 更高优先级指令或必选 Skill |
| 能力交接 | 在请求边界接受的一次能力状态转换 | 项目方法进入下一阶段的审批 |

## 职责与非目标

本项目拥有：观察结果、Skill 候选建议、路由能力状态、physical model/thinking 派发与相关分支记录。

本项目不拥有：项目规格审批、Skill 方法状态机、用户工具权限、业务验收／发布状态。它可以观察这些事实，但不能根据分类器输出伪造它们。

不在本版实现：

- 第二个可调用工具、修改工作区的 observer agent；模型依次互相审查的无限链路；
- 流式 token 级审核、内容合规平台或对所有回答正确性的保证；
- 自动安装、编辑、强制选择 Skills，或执行推荐 Skill 内的脚本；
- 从任意 Skill Markdown 自动提取可执行审批状态机；
- 跨 session 编排、并行子代理、自动部署或业务完成判定；
- 绕过 Pi／权限扩展，或以 Jev 的 grant/readiness 标签直接放行工具；
- 跨物理模型 KV/cache 迁移、账单保证或声称少用高模型必然更便宜。

## R1：观察者输入与单一判断职责

**用户故事**：作为 Pi 用户，我希望扩展理解整个任务背景，而不是把短消息当成简单任务或另一个流程。

1. WHEN 有新实质性用户消息 THEN 系统 SHALL 向观察器提供最新请求以及有界的当前任务目标、消息变更、路由能力状态、已知等待／约束、有效交接摘要和公开执行事实。
2. WHEN 项目启用 Skill 建议 THEN 系统 SHALL 在同一观察输入中提供该运行环境允许自动建议的 Skill 元数据；不得默认读取全部 Skill 正文送往分类服务。
3. 系统 SHALL 优先使用 Jev 作为结构化观察判断器，并由一次主要分类请求合并任务关系、消息作用、工作类型、能力需求和必要的 Skill 候选判断；不得默认串行调用聊天 LLM 二次解释。
4. 观察器 SHALL 无工作区写入和工具执行能力；观察结果必须是有界数据，本地解析后才能参与引导或路由。
5. WHEN 任务状态或目录无法可靠取得 THEN 系统 SHALL 标记缺失，不伪造上下文；可以继续已有派发／不带 Skill 建议的路由。
6. 系统 SHALL 区分模型有效低置信、字段缺失／无效、超时和服务不可用；一项格式失败不得被描述为“用户意图低置信”。

## R2：消息作用与任务连续性

**用户故事**：作为连续开发中的用户，我希望解释、暂停和需求补充正确影响当前任务，不会被另起流程或遗忘约束。

1. WHEN 最新消息仅要求解释当前结论 THEN 系统 SHALL 保留任务身份和已有方法状态，并将本轮工作识别为解释；不得因 explain 自动续做实施。
2. WHEN 用户明确暂停、取消或收紧修改范围 THEN 系统 SHALL 优先使旧待消费能力交接失效，并提供对应引导；不得将这些消息理解成进入下一阶段的许可。
3. WHEN 用户新增需求或约束 THEN 系统 SHALL 记录变更影响，必要时请求高能力收敛；旧范围的授权不得自动扩展到新增范围。
4. WHEN 用户可信地开启独立新目标 THEN 系统 SHALL 不继承旧任务难度、旧 Skill 推荐和旧能力交接；未知关系只能是临时判断，不覆盖已确认事实。
5. WHEN 有明确的纯续接、有效任务与相同配置、未到继承上限且无待重评原因 THEN 系统 SHALL 允许有限复用，不因短句重新选择整套方法。
6. WHEN 方案指代、实施范围或批准含义不明 THEN 系统 SHALL 建议澄清，而不是强行选择标签并表示已获授权。

## R3：不同用户的 Skills 适配

**用户故事**：作为配置了自定义 Skills 的用户，我希望建议来自自己的资源，而不是开发者的个人习惯。

1. 系统 SHALL 使用 Pi 当前运行环境实际解析的 Skill 清单与资源状态作为来源，不自行扫描无关目录构造另一套加载规则。
2. WHEN Skill 被禁用、不可见、仅允许显式调用或没有匹配项 THEN 系统 SHALL 不自动推荐它；显式 `/skill:name` 请求仍由 Pi 正常处理。
3. WHEN 用户明确指定某个 Skill THEN 系统 SHALL 保留该选择，不擅自替换；可报告与任务不匹配或资源不可用，但不得冒称已经加载。
4. 推荐 SHALL 使用运行时可验证的 Skill identity；模型返回不存在的 ID、超出目录的文件路径、未知版本候选或无关名称时不得注入。
5. WHEN 同名、重叠描述或多候选无法区分 THEN 系统 SHALL 给出有界候选或无推荐，不一次要求执行相互冲突的流程。
6. WHEN Skills reload、配置变化、工作目录或 session 改变 THEN 系统 SHALL 使旧目录候选失效；无 Skills 的用户仍可正常使用模型路由。
7. 系统 SHALL 区分“推荐过”“观察到读取正文”“遵循情况未知”；一次 read 不证明已遵循，read 缺失也不证明未通过显式命令或之前上下文加载。

## R4：轻量会话引导

**用户故事**：作为用户，我希望相关方法被提醒而非漏选，同时不被重复建议或另一套流程打断。

1. WHEN 有有效、当前适用的 Skill 候选或需要澄清的消息作用 THEN 系统 SHALL 可以为下一主模型请求提供简短引导，明确“建议考虑／核对”，而非替用户下达新的开发任务。
2. 引导 SHALL 由受控模板和本地验证的标签／目录数据构造；不得直接注入观察模型自由生成的 system 指令或未经验证的路径。
3. 引导 SHALL 不覆盖用户请求、项目指引、原有 system prompt、已加载 Skill 方法或权限要求；原始 Skill description／工具输出中的命令视为数据。
4. 系统 SHALL 对候选数、字符数、每任务／回合建议次数和记录大小设置有界预算，并在相同任务、消息作用和目录版本下去重。
5. WHEN 用户忽略或拒绝建议、已经选择方法，或模型已经有相关正文 THEN 系统 SHALL 不反复催促；不得因未采纳推荐强制 continuation、阻止回答或标记业务失败。
6. 引导记录 SHALL 跟随当前 branch，并在换模型时保留必要的方法上下文；不得用旧引导压过新用户消息。
7. 用户 SHALL 能独立关闭引导而保留模型路由。没有有效候选不阻塞正常执行。

## R5：阶段感知能力选择

**用户故事**：作为用户，我希望高能力用于收敛与复杂推理，明确实施使用足够但较经济的模型，而无需手动反复切换。

1. WHEN 下一步为实质性需求收敛、复杂调查／审查、设计决策、任务规划或复杂诊断 THEN 系统 SHALL 使用相应较高能力 profile 的下限；不能仅因 objective 是 review/research 而排除该 profile。
2. WHEN 实施范围、方法和验收已经明确，且当前能力需求允许 THEN 系统 SHALL 可以自动降低物理模型档位或 thinking；明确实施的默认下限不得等同于全部工作降为 light。
3. WHEN 当前实施仍涉及高风险、复杂推理或关键未知 THEN 系统 SHALL 保留／提升能力，不把“implementation”标签当成无条件降档许可。
4. WHEN 一个简短解释或简单问答出现在复杂任务中 THEN 系统 SHALL 保留任务身份，并独立评估本轮能力；不得把整项任务永久改成低需求，亦不得将全部问答强制 heavy。
5. 能力 profile SHALL 不包含工具写权限或规格审批含义；已授权的设计文档编写可以使用高能力，未授权的代码修改不因执行 profile 被允许。
6. 请求能力、保护后的能力和实际 dispatch SHALL 可区分；目标不可用／thinking 裁剪只影响实际派发，沿用现有可用性检查与 fallback。
7. 能力升降 SHALL 有避免边界噪声／振荡的保护；独立新任务不受旧高能力锁定。阈值和窗口由设计明确，不能声称是实测最优。

## R6：不确定性按动作处理

**用户故事**：作为用户，我希望分类不确定时得到稳妥的调查或澄清，而不是退出所有阶段感知能力。

1. 系统 SHALL 保留相关字段的 confidence/probability 和未知原因，不再用全部字段最小值作为所有 profile 与引导的统一启动开关。
2. WHEN 多个候选解释均支持同一个非扩权动作（例如只读审查／调查） THEN 系统 SHALL 允许采用共同动作与相应能力，不要求先精确区分重叠标签。
3. WHEN 不确定项影响实施授权、任务指代、范围或能力降低 THEN 系统 SHALL 不新增权限、不消费不可靠交接、不据此降档，并可以建议澄清。
4. WHEN 不确定的是 low/medium 风险差异而当前工作是调查 THEN 系统 SHALL 不因此排除高能力调查；风险 label 与风险 label 的置信度必须区分。
5. WHEN 分类不可用／结构无效 THEN 系统 SHALL 保持已确认状态和物理派发的兼容兜底，不生成假的观察建议；失败后何时重评必须有界。
6. 数据形状、枚举、数值和概率规则 SHALL 本地校验。服务返回概率精度与归一容差必须有明确依据和边界测试，不为通过样本随意放宽或伪造概率。

## R7：请求边界、受控交接与不抢占

**用户故事**：作为长任务用户，我希望同一 run 内能够在真实工作变化后换模型，但不受逐工具／逐 token 的抖动影响。

1. 系统 SHALL 在新的实质性用户回合请求前进行主要观察；同回合重复 route、ordinary continuation 和 retry 不重复计为新用户判断。
2. WHEN 有明确能力交接候选或支持的重要执行事实 THEN 系统 SHALL 在后续请求边界评估；事实可以标记待重评，但任意工具结束、provider retry 或自然语言“完成”不直接授权切换。
3. WHEN 同一 run 内准备从高能力收敛降到明确实施 THEN 系统 SHALL 要求有界交接材料和本地接受记录；观察／readiness 只验证能力交接，不替代项目审批。
4. 普通 continuation SHALL 沿用本轮实际 physical model/thinking；retry SHALL 不消费交接；不更改已发送／正在生成的请求。
5. WHEN 新用户 steering、暂停、取消、手选模型、branch 切换、目录／策略改变或等待批准使候选过期 THEN 系统 SHALL 在提交观察结果和消费交接前复验 identity，丢弃不再适用的结果。
6. 系统 SHALL 对每任务观察请求、交接转换、transport retry 和自动注入设置预算；不在流式 token 上持续审核，不建立定时轮询或无限 observer→main→observer 环。
7. 系统 SHALL 不因规划模型自然结束、未读推荐 Skill 或没有 handoff 自动续写开发工作；换模型必须附着既有用户／模型工具 continuation 或明确允许的执行，而不制造实施授权。

## R8：方法与权限不被接管

**用户故事**：作为使用不同方法的用户，我希望路由器适配自己的 Skills，而非改变其审批与开发步骤。

1. WHEN 用户／项目／已选方法要求等待批准 THEN 系统 SHALL 观察等待状态，保留合适能力并停止自动交接推进；Jev ready 不构成批准。
2. 系统 SHALL 不强制建立统一“需求→设计→实施→验证”方法链，也不规定用户必须生成某些文档、通过某个测试命令或使用某个 Skill。
3. 系统 SHALL 不仅因为 routing profile 是 planning/recovery 就禁止所有文档写入；本项目不建立通用权限系统，既有用户约束和权限机制继续适用。
4. 系统 SHALL 不把移除旧 phase-specific guard 解读成新增修改授权；新模式启用前必须通过迁移、安全边界和项目约束回归验证。
5. 能力交接／路由过程结束 SHALL 不被显示为业务验收完成；验证命令事实仅为观测证据，不能替代全部验收条件。
6. WHEN Skill 方法与观察建议不一致 THEN 系统 SHALL 保留其来源差异，由执行模型遵守实际指令与必要澄清；观察建议不得升级成更高权威来覆盖方法。

## R9：启停、兼容、隐私与可观测性

**用户故事**：作为安装扩展的用户，我希望可控启用观察能力，并知道额外请求、建议和派发发生了什么。

1. 用户 SHALL 能独立配置整体路由、观察引导、Skill 建议与阶段能力切换；新观察模式在完成验证前显式 opt-in，不静默改写个人文件。
2. WHEN 观察模式关闭、使用手选物理模型或 direct 调用 THEN 系统 SHALL 不注入观察引导，不劫持原生模型/thinking 行为；原有 router direct/disabled 语义保持兼容。
3. 新观察模式与旧阶段编排控制 SHALL 不同时作为权威 owner 运行；模式冲突必须明确提示，默认优先／迁移规则须在设计中固定。
4. 状态 SHALL 为版本化、有界、JSON 可序列化，随当前 branch 在 reload/resume/fork/tree/compaction 恢复，不读取 abandoned branch 作为补充证据。
5. SDK adapter 无法获取完整 Skills／事件能力时 SHALL 报告覆盖不足，禁用对应建议，不声称完整监测；旧状态可保留同轮 dispatch，但不能伪造新观察或已接受交接。
6. 系统 SHALL 对请求正文、公开摘要、Skill 元数据、候选和记录设明确预算；不发送／保存 hidden thinking、凭据、配置敏感字段、完整工具参数／输出或图像数据。用户输入和 description 可能含敏感信息，截断不等于通用脱敏。
7. 文档 SHALL 告知新增 Skill 元数据可能发往配置的观察服务；Skill paths 留在本地用于验证／读取，不默认作为外发输入。目录来源与项目 trust 仍遵守 Pi 行为。
8. 诊断 SHALL 区分观察／复用／失败、Skill 推荐／已观察读取／遵循未知、候选／接受／实际切换，以及所需能力／fallback；仅 TUI 使用 UI，非 TUI 能保留结构化摘要。
9. 系统 SHALL 记录调用来源、延迟和实际报告的 usage，区分单次多问题与独立交接调用；价格为 0／usage 缺失不得显示为免费。
10. 调用预算、输入预算和取消信号 SHALL 覆盖观察请求与服务 transport；失效结果不注入也不改变模型，已发生的 API 用量不伪装为没有调用。

## R10：迁移与验证证据

1. 新需求批准后 SHALL 明确标注被替代的旧需求／设计条款，再进入实施；本草案不能直接作为已批准代码变更授权。
2. 迁移 SHALL 保留模型/认证可用性、thinking 裁剪、ordinary sticky、retry、user supersession、branch 恢复、取消和 fallback 的回归保障。
3. 新模式 SHALL 不继承旧 reminder/blocked/complete 的业务解释；旧 accepted event 只能按显式版本兼容规则处理，不因 phase 名字相同直接消费。
4. 测试 SHALL 包含下表场景、不同用户 Skill 目录、无 Skills、不同目录版本及错误候选；Skill 推荐质量与能力路由正确性分别报告。
5. 离线测试 SHALL 与真实服务证据分开；真实验证使用临时设置、无敏感样本、有限用量并经当时用户允许，不修改个人持久配置。
6. 原型和小样本结果 SHALL 保持探索证据身份；未验证的 Skills 组合、概率精度契约、长轨迹及 provider/cache 行为必须明确记录。

## 与旧方案的迁移关系（已确认方向，具体映射见设计）

| 既有行为 | 新方向 | 影响 |
|---|---|---|
| 每个新回合强制重新猜 objective/start | 任务状态＋消息作用＋工作需求 | 保留可信续接；解释不重置方法 |
| 所有 choice 取最小值后用统一 0.8 控制启动 | 字段级不确定性与动作级策略 | 改写旧 R1.5；不得顺带放宽实施交接 |
| review/question 不进入 workflow | 调查/审查可有能力 profile，简单回答不强制流程 | 消除意图标签与能力 profile 的硬耦合 |
| planning/recovery 统一禁止写入 | 能力、方法、操作约束分离 | 改写旧 R3；保留外部权限和显式用户约束 |
| 自然结束时 reminder，继续或 blocked | 观察建议不创造新的开发执行 | 退休旧 R6 自动催促；不影响既有用户队列 |
| 强制 execution→verification→complete | 方法自己决定顺序，交接仅为换模型 | 改写旧 R7/R9 complete 的业务解释 |
| 显式 accepted handoff 才能同轮换模型 | 保留为受控能力交接，可调整字段/命名 | 类型、版本、旧事件迁移须在设计中明确 |
| 三档/bands、sticky、fallback、branch state | 保留 | 不改变已发送请求与物理目标可用性 |

新旧模式互斥已确认。旧 `workflow.enabled` 配置如何映射、短期 legacy 的保留及退休步骤由设计明确；需求批准本身不改变既有运行行为。

## 已确认的默认方向与初始预算

- **观察模型**：继续以 `typesafe/jev-latest` 为默认，不增加聊天 LLM；可配置观察模型的范围留待设计，不能路由到 gears/auto 造成递归。
- **引导强度**：启用新模式后，只注入候选提示，不自动读取全文或强制执行 Skill。
- **推荐预算**：每次最多 2 个候选、引导最多 800 个 Unicode 字符；相同任务/消息作用/目录不重复。大 Skill 目录的召回预算须在设计中明确，不能声称完整覆盖。
- **观察时机**：主要在实质性新用户回合、有限继承到期及真实能力交接时；重要工具事实先标记 dirty，不每条工具结果都调用。
- **启停**：新模式默认关闭；仅本次规格批准不修改任何用户的现有设置。新旧配置冲突和迁移提示须显式决定。

以上预算是讨论初值，不是性能／质量实测保证。

## 已确认边界与设计待决事项

用户已接受以下三项建议：

1. **Skill 引导保持建议模式。** 只做有界候选提示，不自动加载全文、强制执行或自动安装。自动加载不属于本版需求。
2. **同一 run 换档要求显式能力交接。** 不依赖被动观察助手自然语言就降档；重要执行事实可以标记待重评，但不是另一条自动换档入口。
3. **新旧模式互斥。** 具体配置迁移、旧 event 恢复及 legacy 保留/退休由设计明确；不能静默移除已启用的保护。

设计阶段固定：字段枚举与授权事实的表示、runtime Skill 清单获取 seam、Pi 请求顺序与注入接线、概率精度规则、采样／目录预算、能力 profile 与旧窗口关系、诊断/配置形状及版本迁移测试。设计获批前不进入任务实施。
